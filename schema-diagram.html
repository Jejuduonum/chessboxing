Relationships

    Why it is shaped like this

    One row per user, cascading
    A trigger on sign-up creates the profiles and user_settings rows. Every table points at auth.users.id with on delete cascade, so deleting an account leaves nothing behind.
    The goal lives in user_settings
    The app runs one goal cycle at a time, so the dates, ratings and weights are columns on the settings row rather than a separate plans table. Starting a new cycle overwrites them.
    How sync resolves conflicts
    updated_at is the device's clock and decides last-write-wins — a trigger rejects writes older than what is stored. synced_at is stamped by the server and used as the pull cursor. deleted_at marks soft deletes so removals reach every device.
    Reviews are stored whole
    A review is one jsonb document — engine verdicts, best moves and coach notes — keyed by the Lichess game id and capped at 400 KB. Nothing inside it needs querying.
    Server-only, by omission
    coach_usage has row-level security enabled with no policies at all. Only the service-role server writes the per-account rate-limit rows, and no client can read another account's usage.
    Not in the schema yet
    The earlier draft's plans and mascot plan_promotions tables are not implemented. The Lichess rating cache stays in the browser's local database and is re-fetched per device, so it never syncs.
